# Picture descriptions and recovery evidence

Pictures can carry usage-specific meaning on each item, recipe, objective, guide, map or location. In either guided editor, include **Image descriptions**, add an entry for an attached asset ID and enter a short description of what the image conveys in that record. If it conveys no information, choose **Decorative** and leave text empty. Rights/attribution are separate and remain visible.

Repository Content Studio's picture workbench also offers description and decorative controls when attaching or reusing a prepared picture. Library-only pictures do not acquire record-specific meaning. Reusing the same asset on another record can have different descriptions. Existing records can edit these entries in the guided fields. A blank optional workbench description preserves legacy/generic behavior rather than inventing visual facts.

The optional `imageDescriptions` array has at most nine unique attached asset IDs, each with `assetId`, `text` (maximum 1000 characters) and `decorative`. Decorative text must be empty; meaningful text cannot be whitespace-only. Updated readers accept legacy packs without this field and use a generic label that explicitly says no description was provided. Older strict-schema readers may reject enriched packs; this is not a promise of backward compatibility with old readers. Content/picture/recovery transfers retain the field and validate it before saving. Removing an image in Studio removes its usage description too.

Read-only recovery diagnostics report retained transaction/file counts and bytes. Incomplete scans show partial totals, not a misleading complete estimate. A transaction is eligible for manual archival review only when its completed receipt and retained backup hashes agree and there is no pending/locked/uncertain state. Nothing is archived or deleted automatically. Eligibility does not mean deletion is safe: historical receipts support repository change tracking, including removed paths.

The release manifest inventories every shipped payload file, including launcher, instructions, license and documentation. Its own name is included but its self-digest is explicitly excluded to avoid circular hashing. Build identity records observed stable source hashes, captured catalog/media hashes and exact generated output hashes. It is not authenticated executing-code provenance. Later author saves do not invalidate a correctly captured older build; changed generated output or static source does require rebuilding before packaging. Git revision/dirty state is descriptive only. Hashes demonstrate internal consistency, not authorship or authenticity: someone replacing both a payload and its manifest cannot be detected without separately trusted evidence.
