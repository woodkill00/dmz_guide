# Existing foundations and design decisions

Observed in current checkout: Content Studio already resolves catalog identity and edits six public record groups using guided typed fields, sources, a media library, author-local preview, revision checks and recovery journals. Private /editor/ and /local/ are separate browser-pack tools; their saves do not change repository files. Mission audit stores editorial review states independently of mission content/progress. Images currently attach as one primary plus eight additional IDs with contextual descriptions; there is no general section/block layout document.

Owning sources: docs/content-studio.md, docs/mission-directory.md, src/content/author-target.mjs, src/content/validate.mjs:151+, src/ui/author-actions.mjs, src/ui/editor-page.mjs, src/client/local.mjs, schemas/pack.schema.json. Existing generalized authoring should be extended, not replaced with an unrelated service. Specialized catalogs require inspected adapters; a universal UI cannot assume all records share the pack schema.

User selected repository save. Therefore use the current loopback author server as the write boundary. Personal browser packs remain compatible, but implementing a second private page-document editor is out of scope. The future public-approved-account requirement is recorded as a separate authenticated backend phase; the current reader remains static and read-only.

Choose validated content blocks with stable IDs rather than arbitrary contenteditable HTML or a free-position canvas. This permits reliable image placement, source-update comparisons, mobile reflow, undo and deterministic previews without executing imported content. Managed data blocks project canonical facts and cannot be replaced by manually copied tables that drift from calculations. Keep page documents outside pack-v1 records so old portable content is not silently extended; include them through a separate versioned build manifest and explicit new page-bundle format.

Pictures reuse existing raster normalization, asset library, rights metadata and bounded transactions. Placements hold contextual alt/caption/layout; asset identity/hash/rights remain shared. Replacing a placement never deletes shared bytes. Gallery navigation is bounded and keyboard operable. W3C image guidance distinguishes meaningful alt text from decorative empty alternatives: https://www.w3.org/WAI/tutorials/images/ .

Drag is optional convenience, with keyboard and single-click Move controls. W3C distinguishes keyboard access from the non-drag pointer alternative: https://www.w3.org/WAI/WCAG22/Understanding/dragging-movements . No external editor framework is selected before a prototype proves it can respect the existing static architecture, accessibility and bundle budget.

Capacity proposal: page document v1 <=256KiB,32sections/128total blocks,2000characters per prose field,9distinct attached image IDs, tables<=50rows/8columns/500characters per cell, two-column groups one level deep. Existing global metadata, asset, transaction and portable limits still apply. If a nine-picture record cannot fit the existing 8MiB portable image budget, export explains the bound and offers smaller batches or references-only output; never silently omit pixels from a claimed self-contained backup.

Key risks: specialized adapters missing fields; schema/backup incompatibility; confusing draft/repository/build states; accidental progress edits; title-based matching; orphaned assets; stale section links; provider refresh overwrites; huge previews; public exposure of local writes. Every risk maps to contracts/tasks/tests. Repository-wide roadmap work remains separately prioritized, not bundled into this editor implementation.
