# Data model and contracts

Public snapshot exact version=1,updatedAt(YYYY-MM-DD),coverage(nonempty<=1000),sources(array<=32 exact id/title/url/date/status),weapons(array<=256 exact id/name/category/sourceIds),blueprints(array<=512 exact id/weapon/name/variant/method/sourceIds). Strings inert; URLshttps allowed publisher/direct providers, no credentials; IDs lowercase slug<=100. Duplicate IDs and normalized weapon/name/variant identities rejected. Every blueprint weapon and source reference must resolve. Source status official or reported. Released roster only; no assumed individual manual applicability from collection-monitor totals. Empty variant is ordinary; named variant e.g.BlackCell is editorially separated, stored key `Name · BlackCell`.

Private workspace v1 exact existing top-level fields unchanged. Acquisition entry required manual(boolean),attachments(array),blueprints(names) and optional manualExtractions(safe integer0..9999). Existing limits unchanged. Absence is unknown. Counts do not imply ownership and vice versa. Additional optional field recognized by current validator and portable backup; legacy backups accepted without rewrite. Any legacy IDs/names/observations remain retained.

Mutation uses `saveArmory(candidate, expectedRevision)` and same previous-snapshot envelope. No new profile store. Reads use readExistingRecord for bounded discovery, validate before projections and retain corrupt bytes; mutations unavailable until storage/candidate valid. Transaction completion determines saved state; painting is separate. Stale/quota saves retain exact candidate/original expected revision. Retry does not recalculate a delta; reload confirms discard. Export unsaved candidate uses the existing armory backup envelope and includes only selected pending edit; unsaved numeric/text drafts stay on screen until canceled/saved.

DOM contract: main `#weapon-acquisition`, `#acquisition-roster` contains stable weapon details `[data-acquisition-weapon]`; legacy workbench has its own same selector on separate route. Controls scoped to data-manual/data-count-step/data-count-form/data-known-blueprint. Refresh syncs nodes, respects drafts and does not close details or recenter. Menu links native. Store facts publicly refer to snapshot known ownership denominator, not complete-game denominator.

Catalog admission: max512KiB serialized UTF8, depth8, nodes25000; all objects plain and exact. Scalar text lengths: id/weapon<=100, weapon name<=100, class from fixed9-category allowlist, blueprint name<=80, variant<=30, final owned name<=100, method<=500, source title<=160, source URL<=1000, date exactYYYY-MM-DD, coverage<=1000. Nonempty required strings; control characters rejected. Sources<=32,sourceIds<=8 perrecord, arrays have unique entries. Each source URL is HTTPS, no credentials, approved fixed publisher/direct-provider host. Every reference resolves; duplicate weaponIDs/blueprintIDs and normalized final owned-name collisions within a weapon rejected. Normalization NFKC, typographic apostrophe→ASCII, trim/collapse spaces and lowercase; no fuzzy weapon matching. Variant storage `Name · Variant` is only accepted when that FINAL normalized key is unique, including against a literal name containing the separator. Test malformed/oversized strings, bytes/nodes/depth, danglingrefs, unsafeURL, variantcollision, duplicateIDs and invalidcategory/date.
