# Contract: confirmed upgrade spending (2026-10-26 amendment)

This supersedes the earlier no-purchase scope restriction, not the status-only correction contract. A purchase records an in-game action the player says occurred. It never invokes the game, verifies eligibility or reconstructs old spending.

## Strict profile v3 and history shape

V3 structural inventory/reserve maps allow integers0–2,000,000 so the observed Bank IV capacity can be entered; this is an input allowance, not an inferred holding or verified universal game maximum. Known non-currency items remain capped at1,000,000 in selected-pack validation, draft/HTML controls and purchase snapshots; known currency stock/reserves allow2,000,000. Unresolved imported IDs retain structurally valid values without clamping. V1/v2 stock/reserve caps and all requirement/goal caps remain1,000,000.

V1/v2 remain valid and read-only for spending; their existing manual progress behavior is preserved. Fresh pack-v2 profiles use v3. Explicit migration takes v1 through the existing upgrade mapping and adds empty `spendHistory`; v2 fields are copied unchanged. No event is invented for old completed entries. Previous snapshot retains the exact original version. Older code rejects v3 rather than stripping history.

`spendHistory` is an ordered array, maximum **500 events**. A purchase may append only while at most 498 events exist, reserving a reversal slot. Every candidate remains within the existing **1 MiB, depth 12, 20,000 nodes** profile bounds; also validate a worst-size safe-reversal candidate before admitting a purchase, so immediate undo is not blocked merely by capacity. Never truncate or compact history to fit.

All IDs are existing namespaced IDs, maximum 100 characters. Every event ID is unique and generated once per UI preview (`spend:<UUID>`). `recordedAt` is a canonical ISO UTC timestamp (24 characters); it records guide entry time, not gameplay capture time.

Purchase event has exactly:
- `id`, `kind: purchase`, `recordedAt`, `contentVersion` (maximum 80 characters);
- `upgradeId`, `upgradeName` (inert text, maximum 200 characters), `scope` (game/mode/build snapshot under existing scope bounds), sorted unique `observationKeys` (maximum 100 keys, each maximum 100 characters);
- `beforeProgress` (null for absent entry, otherwise the exact validated upgrade-progress entry), `afterProgress` (same availability/legacy annotation, completion completed, reviewRequired false);
- `costs`: 1–100 unique item IDs sorted stably. Each row has exactly `itemId`, `name` (maximum 200 characters), `kind` and `unit` (existing compatible item kind/unit enums), `consumed`, `retained`, `before`, `after`, `reserve`. Consumed/retained costs are integers0–1,000,000. Before/after/reserve are integers0–2,000,000 for currency snapshots and0–1,000,000 otherwise; consumed + retained > 0, after = before − consumed, after >= retained + reserve. Repeated consumed rows sum and retained rows take the maximum floor. At least one positive consumed cost is required to record spending.

Reversal event has exactly `id`, `kind: reversal`, `recordedAt`, `purchaseId`. It references a prior purchase once, not another reversal; original snapshots remain untouched. It is not a game refund. Validation replays only the bounded event-state machine (never inventory effects): every purchase must have no concurrently active equivalent scoped purchase, and each reversal must reference the latest then-unreversed purchase. Identity unions persist through reversals. Validation rejects duplicate operation IDs, forward/missing references, non-latest or repeated reversal, concurrent alias purchases, malformed arithmetic, unit/kind mismatch and all unsupported fields before save/restore. Snapshot data is inert/private; imported events are records, never executable actions.

## Purchase transition

`recordUpgradePurchase(pack, profile, upgradeId, { operationId, recordedAt, expectedRevision })` returns `{ candidate, event, changed, warnings }` without writing storage. The UI persists the candidate once using existing atomic profile CAS. `spendingTotals(profile, optionalPurchaseFilter)` derives totals; `recordSpendingReversal(profile, purchaseId, options)` returns the same transition shape without reading current costs.

Admission requires selected compatible content version, profile v3, matching expected revision, visible one-time upgrade and all visible consumed/retained items, compatible item scopes, positive known quantities, known consumed/retained semantics, no disputed/unknown cost evidence or conflicting scoped aliases, entered stock for each listed cost and enough stock to preserve retained floor plus fixed reserves. No prerequisite or crafting costs are charged implicitly. Unknown build/prerequisites, availability or legacy requirementsKnown=false coverage are explicit warnings when every listed row is exact: they do not block bookkeeping for a purchase the player confirms occurred.

Purchase identity is the tuple (full gameId/mode/build scope, upgradeId), unioned transitively with equal observationKeys within that same full scope. ID matching is scoped, not global; different scopes never alias. provenance.lineageKey alone is not a purchase identity and MUST NOT be used for deduplication. Any completed current alias or active purchase snapshot in that scoped identity group blocks another purchase. Current aliases must agree on exact costs; no representative ordering discards disputes. Historical active purchase snapshots also participate in identity matching, preserving retired IDs/keys and bridges across content changes. An ordinary progress correction/reset cannot remove this guard. Reusing an operation ID for a different target, kind, timestamp or reversal target is rejected; replay of the same recorded operation returns unchanged state, not a second debit. UI pending-save serialization and storage CAS remain independent defenses.

Before building or displaying a preview, if the upgrade or any required consumed/retained item is hidden, refuse with a generic reveal-spoilers instruction without exposing names, counts or costs. Otherwise preview displays every deducted amount, retained floor, reserve, before/after stock, resulting completion and counter change. It explicitly asks the user to acknowledge **“My saved stock is from before this purchase; these costs have not already been deducted.”** If stock was already adjusted, offer the existing **status-only correction (no spending recorded)** route instead. No default checked acknowledgement; Cancel changes nothing. Reserved stock is never overridden here: change reserves separately, save, then make a new preview.

## Correction and safe reversal

Manual progress/availability correction and both progress/profile reset preserve spendHistory and do not debit/refund. Reset may clear other private fields, but its copy explicitly says spending history and active-purchase guards are retained. Backup restore is a separate explicit whole-profile replacement, with before/after history coverage/count/totals shown; restoring an older history-less profile requires an explicit warning, retains the previous profile and never replays purchases.

A reversal is allowed only for the **latest currently unreversed purchase in array order** (reverse order of entry, not user-editable timestamp), with every affected inventory key present and equal to its recorded after value, the target progress entry exactly equal to afterProgress, at confirmation. Matching current values is a conservative bookkeeping guard, not proof that no intervening gameplay occurred. The preview uses original snapshot costs/units even if the catalog changed or the ID retired. It restores before quantities and beforeProgress (including true absence) and appends one reversal. Reserves/goals/pins/routes are unchanged. Reject missing/edited affected stock, changed progress, arithmetic overflow or capacity atomically; explain manual reconciliation instead. A reversed purchase may be recorded anew only after a fresh explicit purchase confirmation; ordinary repeated Undo never refunds twice.

## Counters and privacy

Show **Recorded usage/spending**, not all lifetime gameplay. Primary totals are net = gross purchases − reversed purchases, with gross and reversed amounts visible. Overall material total includes only non-currency `unit: count` rows. Each item identity/kind/unit has a separate breakdown; each currency ID is separate even if units match. Other resource-unit quantities remain separately labeled, never added to item counts or cash. Totals use immutable snapshots, never current catalog costs/names/units, and aggregate safely <=10^12.

Old/manual completed upgrades and prior/imported backup gaps are explicitly **spending not recorded**; empty history means zero recorded usage, not zero past gameplay spending. Inventory edits never add events. Restore imports/replaces history, not an accounting replay. Totals and history are private profile data and never included in public content exports.

While spoilers are hidden, only events whose upgrade and every cost item resolve to currently visible non-spoiler records may enter displayed rows/totals. Omit the entire purchase and matching reversal otherwise; show a generic partial-display notice without hidden counts/labels/amounts. Guard all snapshot names against spoiler substrings. Revealing spoilers permits the full private history, including retired IDs. The same safe projection/no-hidden-count policy applies to purchase, reversal, reset, migration and restore/history-replacement summaries. A restore with hidden history uses a generic history-replacement warning, not raw event counts or totals. Totals APIs may compute full private totals for validation/export; UI must use the safe projection. Render at most 50 history/breakdown rows per page.
